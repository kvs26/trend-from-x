# X Idea Scout

Find a small product worth testing, grounded in current conversations and a credible way to reach users. Prefer a candid rejection over an attractive idea with weak evidence. This project is for scouting, evaluation, discussion, and portable briefs. Product implementation and the actual build harness belong in a separate folder and session chosen by the user.

## Start with the current request

Use the user's current request to set the research scope. When continuing or revisiting an investigation, read its relevant report under `research/x-ideas/`. For a fresh scout, use earlier reports for history and deduplication without assuming their niche, business model, audience, or recommendation still applies. Explore credible alternatives and seek evidence against preferred ideas. Ask only about missing constraints that materially affect the current task; do not repeat a full onboarding interview.

If `IDEA_DIRECTIONS.md` exists at the project root, read it as user-curated context. It contains broad directions rather than selected products and does not restrict every research run. Edit that file only when the user explicitly requests adding, changing, removing, or updating directions in it. Routine scouting, new findings, enthusiasm about an idea, or a request to save research does not authorize an edit, including status or date changes. Suggest possible additions in conversation and keep research in the normal reports until the user asks to change the directions file. This rule is separate from updating research reports and an existing index.

Do not ask the user to choose useful tools versus playful experiences. Explore both useful and playful opportunities unless the current request specifies a narrower interest. A stated product interest guides relevance within the selected research options.

## Select research options and lookback period

At the start of each new research invocation, read [the X account watchlist](references/x-account-watchlist.md) and ask which **one or more research options** the user wants. Show the six account categories with their names, current account counts, and short plain-language meanings. Add **7. Free X search — search across X for relevant problems, launches, results, and conversations beyond the curated accounts; no fixed account count.** Allow this option on its own or combined with any categories. Use the category meanings in the watchlist; do not present unexplained labels. Include **All watchlist categories** with the total unique account count; this selects the categories, and free X search is included when also selected. Calculate counts from the actual entries so additions or removals do not leave the menu stale.

Support multiple selections in a single answer. Use a multi-select control when available; otherwise show a numbered menu and accept comma-separated numbers, category or option names, or "all categories" (for example, "2, 3, 7", "7 only", or "all categories + free search"). Do not use a single-choice control that prevents selecting several options. If the user already specified categories, all watchlist accounts, or free X search in the invocation, use that selection without asking again.

Also ask **"How far back should I look for posts?"** Offer examples such as the last 7 days, last 30 days, last 3 months, or a custom duration or start/end date range. These are suggestions, not limits or a fixed one-month minimum. Accept any clear period the user specifies. Ask for research options and the period together when possible, and accept a combined answer such as "2, 3, 7; last 2 weeks". If either choice is already supplied in the invocation, ask only for the missing one; if both are supplied, start without repeating the questions.

Wait for both the research options and period before research; do not assume either after a timeout or silently default to a month. Convert the chosen period to explicit start and end dates in the user's timezone, using the run date as the end for a relative lookback unless the user specifies otherwise. State the selected options, dates, and total unique watchlist accounts, if any; free search has no fixed account count. Start without another product-direction interview.

Keep the options and date window for follow-ups in the same run. Ask again for a fresh research run unless its request already supplies them. A follow-up may change the window, add categories, or add free X search; complete the added scope without repeating finished coverage. Do not store these run-specific choices as permanent preferences.

## Required account-by-account research

When the selection includes watchlist categories, inspect **every account in those categories individually, one by one, in watchlist order**, covering **the user's chosen date window for each account**. Selecting all categories includes the entire watchlist; otherwise unselected accounts are outside the required pass. Deduplicate accounts if categories overlap. Apply the chosen period as stated, including periods shorter than a month; do not impose a separate minimum. Follow [the research playbook](references/research-playbook.md) for the account pass and evidence capture. Do not substitute a handful of recent posts, a sample of selected accounts, a combined search, or broad keyword searches for the required individual checks. Do not stop after finding a few attractive ideas. Free X search alone does not require a watchlist pass.

Keep a coverage record for every account, including the required and actually inspected date ranges, access level, and relevant findings. When a completed inspection yields no useful signal, explicitly say **"Nothing relevant found"** for that account and give the inspected window; do not force an idea from every person. An inaccessible account or a partially inspected date window is an access or coverage limitation, not a no-findings result. If interrupted, preserve the completed coverage and next account, then resume the remaining accounts before treating the pass as complete. Report actual coverage candidly when access prevents completion.

During each account's inspection, open referenced or quoted posts and follow relevant source chains deeply enough to understand the original evidence, thread, and context. Follow references outside the watchlist or chosen date window when needed; record their dates and discovery path and label them as context outside the selected period. This does not silently expand the main search window. Do not postpone essential reference checks until a follow-up. After the required pass, expand promising replies, linked builders, and independent corroboration as useful. Present all relevant findings in chat and an overall top five. A follow-up can dig further into older posts, reference chains, replies, or selected opportunities using the completed findings and resuming any unfinished coverage; it does not restart the entire pass unless the user requests a fresh scan. A request to maintain the skill or its watchlist is a maintenance task, not a research invocation.

When free X search is selected, follow the playbook's free-search route: discover posts across X through adaptive topic, problem, launch, and result searches, then inspect originals, replies, and referenced posts. Use the user's chosen date window and record actual search coverage. Free search is discovery, not an exhaustive review of X or every discovered author's history. When combined with categories, apply the same selected period to both routes, complete the selected account pass, and add the free-search findings; deduplicate shared evidence. Apply the same evidence standards and overall top-five evaluation to both routes.

Choose the scope from the request:

- **Scout:** Complete the selected account pass and/or free X search, present all relevant findings, and rank the top five opportunities across that run's findings. This is the default.
- **Investigate:** Test a supplied post, product, audience, or idea against demand, alternatives, distribution, and costs.
- **Prepare a portable brief:** Once the user selects an idea, use [the build handoff](references/build-handoff.md) to produce a self-contained brief for a separate project folder and session. Keep product code and build-harness setup out of this scouting project.
- **Revisit:** Update a previous candidate using new evidence or actual launch results; preserve earlier decisions and explain what changed.

Investigation, comparison, ideation, and a portable brief follow the selected research route on a new research invocation. When the user requests them as follow-ups, work from the current run's evidence and gather the additional evidence needed for that request.

## Research and judgment

Use [the research playbook](references/research-playbook.md) for search strategy, evidence capture, and evaluation. X is the primary discovery source; official product pages, documentation, and pricing help establish competition and feasibility.

Originality is not a requirement. Established product categories, very similar alternatives, and close functional replicas are valid candidates. Existing customers and purchases can provide evidence of demand; the existence of a competitor alone does not prove or disprove an opportunity. Do not reject a finding or downgrade an idea merely because it has already been done, and do not require a novel feature, underserved niche, or moat. A similar product serving the same audience can qualify through credible customer access, competent execution, and workable economics. Look for a reachable share of demand sufficient for the founder's goal; a large market is a hypothesis to investigate, not a guarantee of customers. Present optional differences such as price, service, language, or workflow fit when supported, without inventing a differentiator to justify entry.

The user's Chrome session previously supported reading X and searching posts after the user signed in. That is historical evidence, not a guarantee that a future session is available. Discover current browser tools and inspect current state; never reuse old tab identifiers or assume persistent login. Use computer/browser tools when available. Let the user handle login if needed; do not request credentials or store session material. If X is blocked, report the limitation and continue with accessible public evidence or supplied posts, clearly labeling reduced coverage.

Favor websites and web apps with fast access from a shared link. Consider native mobile only when device capabilities, usage context, or distribution justify it. Consider tools, directories, boards, comparisons, and playful experiences when evidence supports them; do not force everything into subscriptions or an AI wrapper. When evaluating a candidate, target a usable first launch within one week at around 30 hours of founder effort plus agent assistance. Include setup, integrations, verification, and deployment in the estimate; agentic coding does not make external dependencies disappear. Suggest a smaller version or explain the mismatch when a candidate cannot fit.

Treat shareability as a mechanism to explain and test, not a promise. Describe who shares what, why the next person clicks, and what causes further sharing. A prominent person's request can provide a launch opening, but is not a complete acquisition strategy or proof of payment demand.

Separate attention, user value, and willingness to pay. Evaluate trend timing alongside a product's usefulness after the initial spike. Distinguish a small temporary experiment from a product with repeat use and a credible longer-term advantage; neither is automatically disqualified.

## Deliver and remember

The normal flow is **research option selection → selected account pass and/or free X search with reference checks → full findings in chat → overall top five → user-directed follow-up**. State the selected options and date window, plus the watchlist account count when applicable. Group watchlist findings by category and account and free-search findings by theme or conversation. For each relevant signal, give the author, direct post link, post date, concise description of the problem, result, request, or behavior, why it may matter, and any important uncertainty. Distinguish observed facts, self-reported results, and possible product interpretations. Include promising leads found through replies or linked accounts and show their source chain. Report all relevant signals; the top five is an additional synthesis, not a replacement for the full findings. Merge repeated signals while retaining every contributing source. Include the full coverage record for selected accounts, explicitly stating "Nothing relevant found" for completed empty inspections and identifying access or date-range gaps separately. For free search, summarize the themes/queries, date window, and access limits instead of implying exhaustive account coverage. Unselected routes and categories are outside scope. Saved reports support the chat delivery and do not replace it. If necessary, deliver numbered parts without dropping selected accounts or asking the user to narrow the results first.

After reporting the full findings, rank five distinct opportunities across all findings from the selected routes using the playbook's evidence, demand, distribution, sharing, buildability, and economics criteria. Rank proven categories and similar products on those merits; do not give originality an automatic advantage. Explain each one's rank, target user and problem, direct supporting evidence, smallest useful product, sharing or first-user path, concrete earning method, rough effort/cost, main uncertainty, and next validation step. The earning method must name who pays, what they buy, a plausible price hypothesis, and any prerequisites such as sponsor demand or traffic. Combine corroborating signals from multiple accounts where appropriate; do not rank by post popularity or force one pick per category or route. If fewer than five credible opportunities exist, present fewer and explain why rather than filling the list with weak ideas.

Then let the user choose the next step. The top five does not authorize a build decision. If asked to filter further, compare, or dig deeper, work from the findings and gather the extra evidence needed. If asked to think deeply or develop ideas, explore several directions grounded in the findings, such as a narrower audience, a different workflow, a distribution opening, or a combination of repeated needs; label new concepts as hypotheses and explain their evidence and tradeoffs.

When the user requests a recommendation or selects a candidate for deeper evaluation, explain the first-user path, what the user would do personally, an inexpensive test, and measurable continue/change/stop criteria. Work toward at least USD 5,000 in cumulative revenue over six months, with some profit desired. Use revenue scenarios with explicit assumptions instead of income predictions, estimate costs and possible surplus separately, and flag ideas whose economics cannot plausibly support this goal. Recommend passing on all candidates when appropriate.

Honor the user's requested research layout. For the active Plan 1 investigation, maintain the single `research/x-ideas/plan-1-client-experiences.md` report with dated research entries, evidence, decisions, and candidate status; do not create extra dated reports or an index in that folder. Earlier reports are archived under `research/archive/x-ideas/`. For a future investigation without a specified layout, use dated reports and an index only if helpful. Use the user's local date. Capture candidate IDs/slugs, report links, status (watch, investigate, test, build, launched, or passed), decision reasons, and next evidence needed. Deduplicate against earlier runs. Preserve historical observations rather than silently replacing them. Record observed user outcomes separately from assumptions.

Record investigation-specific context and decisions in the relevant research report. Do not create or maintain a separate founder profile. Keep project findings out of the reusable skill instructions. Resolve output paths relative to this project, not the shell's incidental directory.

The user handles conversations, outreach, and posting. Prepare draft posts and replies when useful, without sending them. This skill does not initiate external communications, spend money, configure accounts, schedule monitoring, or install tools merely because they might help an idea.
